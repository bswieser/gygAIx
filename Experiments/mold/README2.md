# **Developer Notes: Document Layout Extraction Engine**

## **Overview of Iterations**

The provided code tracks the evolution of a custom Document Layout Analysis (DLA) engine. The architecture relies on "biological/physics" algorithms (mold growth, bounding box expansion) and Bayesian probability, eventually integrating with Local AI (Ollama) for semantic validation.

### **Version 1: The Base Physics Engine**

* **Key Features:** Introduced the DensityEngine and the run\_physics\_loop. Extracts atomic molds using connected components based on ink density.  
* **Limitations:** Physics expansion was limited to horizontal growth (Left/Right). The merge strategy was a basic single-pass threshold check.

### **Version 2: Advanced Heuristics & 4-Way Physics**

* **Key Features:**  
  * Upgraded run\_physics\_loop to support 4-way directional expansion (Left, Right, Top, Bottom) with randomized processing queues to prevent directional bias.  
  * Introduced a sophisticated 3-pass apply\_master\_combine strategy: Horizontal Contiguous Stitch, Scale-Restricted Containment, and Sub-Average Area Sweep.  
  * Added Human-in-the-Loop (HITL) fallback using ipywidgets.  
  * Added a 16x16 density profile generator for future LLM integration.

### **Version 3: OOP Refactoring & Exact JS Math Parity**

* **Key Features:**  
  * Moved the standalone physics loop inside the DensityEngine class as perform\_physics\_loop, migrating to object-oriented properties (growL, growR, etc.).  
  * Rewrote integral image math (\_get\_region\_ink\_density) to account for OpenCV's exact matrix shifting, ensuring math parity with the original JavaScript logic.  
  * Upgraded the apply\_tri\_split fallback (used for Tables) to evaluate both horizontal and vertical gutters.

### **Version 4: Scale Normalization & Interactive Debugging**

* **Key Features:**  
  * Introduced MAX\_DIMENSION \= 1024\. This is a critical fix: it downscales high-res images before processing so that hardcoded pixel heuristics (e.g., speed=2, radius=8) behave consistently, then upscales the coordinates for the final JSON.  
  * Implemented DEBUG\_MODE with a blocking prompt\_debug\_step using Matplotlib to step through the extraction stages visually.

### **Version 5: Collision Guards & Timed Debugging (Peak Algorithmic Engine)**

* **Key Features:**  
  * Replaced the blocking debugger with a non-blocking, timed visualizer (time.sleep), preventing notebook hangs.  
  * **CRITICAL ADDITION:** Added merge\_would\_collide(). This function simulates the bounding box of a potential merge and aborts it if it overlaps with any other independent region. This prevents the catastrophic UI bug of intersecting bounding boxes.

### **Extension 1 & 2: The VLM/LLM Semantic Pipeline**

* **Key Features:**  
  * Pivots from purely algorithmic layout extraction to an AI QA pipeline.  
  * Uses a Vision-Language Model (gemma4 or olmocr2) to perform localized OCR on the bounding boxes generated by the physics engine.  
  * Uses a pure LLM to perform "Semantic Validation" on the OCR text—checking if the text cuts off mid-sentence or if columns were erroneously merged across gutters.  
  * Generates a semantic\_diagnostics JSON and includes a Matplotlib visualizer to flag problematic chunks for human review.

## **🏆 The "Best" Versions to Consider**

### **1\. Most Robust Core Engine: Version 5 (Snippet 6\)**

If you need a standalone, fast, deterministic algorithm for bounding box generation, **Version 5 is the undisputed best.**

* **Why it wins:** It combines the exact JS math parity, the scale normalization (crucial for dealing with varying document resolutions), and the merge\_would\_collide safety guard. Without this collision guard, the multi-pass merging in earlier versions can easily create overlapping, corrupted zones.

### **2\. Most Innovative/Worthy of Note: The Semantic Validator (Snippets 7 & 8\)**

While Version 5 is the best algorithmic engine, the **Ollama Semantic Validation pipeline is the most significant architectural breakthrough.**

* **Why it matters:** Algorithmic layout engines (even ML-based ones like LayoutLM) frequently fail on edge cases (e.g., merging two separate columns because the gutter was too small). By feeding the extracted text into an LLM and asking *"Does this read like a complete sentence, or did it jump across columns?"*, you create a self-healing pipeline. This semantic layer acts as an automated, highly intelligent QA agent that can flag specific boxes for resizing, bridging the gap between computer vision and natural language understanding.  
* **Recommendation:** Use Version 5 to generate the initial mold\_layout.json, and run the Semantic Validator over the results to achieve near-perfect OCR workflows.
